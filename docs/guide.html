1. What is laravel-workflow?

laravel-workflow is a kit for Claude Code, not a Composer package. Nothing is added to your app's code. It adds instructions and checks to Claude Code, as a plugin or as files in your project's .claude/ folder, and they change how Claude Code works on your Laravel project.

  • It plans before it builds. Opus turns your request into small draft task files with clear "done" checks. You read and approve them.
  • Sonnet builds each task, directly for small tasks and with specialist agents for large ones.
  • A second agent checks the work. It sees only the task and the changes, never the builder's reasoning. A task can't be closed without its verdict.
  • Automatic checks catch the mistakes that only show up in production: env() outside config, mass assignment, raw SQL, a missing @csrf, N+1 queries, and more.
  • It knows Laravel 13 (rules checked against laravel.com), and it uses Laravel Boost when you have it.
  • Post and Page modules always use the Gutenberg block editor, never CKEditor.
  • Pure code. Nothing written for a task carries a comment; intent goes into names, types and small methods. A check blocks any edit that adds one.
  • The decisions stay yours. Claude can't approve its own drafts, accept work nobody could check, or push.
  • It's safe to undo. You can get one commit per task and roll back any single task.
In one sentenceDescribe what you want with /laravel:write-task, approve the plan, run /laravel:task, and every task is built, independently checked and recorded.

3. Installing it: plugin or project files

There are two ways. Pick one per project. If both are present, the plugin says so at session start and the project files win.

Updatingclaude plugin update laravel@laravel-workflowRun ./install.sh again.

A

Install as a plugin

claude plugin marketplace add ~/www/hobbies/laravel-workflow
claude plugin install laravel@laravel-workflow

The commands are the same /laravel:*. A plugin can't carry permission rules, so extra checks take their place: one approves only the kit's own helpers, your test, lint and build commands, a few read-only artisan commands and Boost's read-only tools; one blocks Claude from reading .env files, keys, auth.json and storage/. Your own deny and ask rules always win.

B

Or copy it into your app

cd ~/www/hobbies/laravel-workflow
./install.sh /path/to/your-laravel-app          # add --dry-run to preview

This copies the kit into your-laravel-app/.claude/ and merges settings.json. The old file is backed up, older kit entries are replaced, and permission rules that earlier versions shipped and later removed are dropped. If PHPStan is installed, it also records the findings that already exist, so Claude is held only to new ones.

1

Open Claude Code in your app, then run setup once

cd /path/to/your-laravel-app
claude
/laravel:setup

At start you'll see a short report: kit version, Laravel and PHP versions, the view layer, drivers, storage, the Kit helpers path and the verify commands. That means it's working. Setup creates .claude/tasks/, fills .claude/project-context.md with facts about your repo, adds a short pointer to CLAUDE.md, recommends Laravel Boost if it's missing, and tells you what won't work here.

If setup says static analysis is already failingType ! bash .claude/hooks/verify.sh --baseline in the prompt (plugin: the Kit helpers path from the report). That records the existing findings. Claude isn't allowed to do this itself, so it can never excuse its own mistakes.
CommitWith project files: .claude/ (including .claude/tasks/) and CLAUDE.md, so your team gets the same workflow. With the plugin: .claude/tasks/, .claude/project-context.md and CLAUDE.md. .claude/.cache/ is git-ignored.

4. Laravel Boost (recommended)

Laravel Boost is Laravel's official MCP server. With it installed, the kit's agents use its read-only tools:

Boost toolUsed for
search-docsDocumentation for your exact package versions, checked before relying on memory
database-schema, database-queryReading the real schema and stored data (read-only) instead of guessing
last-error, read-log-entries, browser-logsSeeing the actual exception when something fails
record-ruleTeam-shared project rules in .ai/rules, used by the main session only, never by agents
composer require laravel/boost --dev
php artisan boost:install          # choose Claude Code: guidelines, skills, MCP

Claude Code asks once to approve the project's .mcp.json server. The read-only Boost tools are then pre-approved (by permission rules with project files, by the plugin's check with the plugin).

5. Your first task: plan, approve, build

1

Describe what you want

/laravel:write-task an admin screen where editors manage their own news and can delete one

The planner (Opus) asks questions first if something is unclear, splits big requests into small tasks, sets the order (depends) and size, and writes them as drafts. It never writes code.

2

Read the drafts, then approve them in your own terminal

---
id: 003
title: Editors manage their own news
status: draft
depends: 002
size: large
---
## Goal
Editors see and delete only their own news items in the admin area.

## Acceptance
- [ ] [test]    Deleting another user's news returns 403 and deletes nothing
- [ ] [browser] Guests are redirected to "/"
- [ ] [review]  Authorization lives in a NewsPolicy

Each "done" check carries a tag saying how it will be proven:

  • [test]: a Pest/PHPUnit test must prove it.
  • [browser]: it has to be seen in the running app.
  • [review]: reading the code is enough.
bash .claude/hooks/tasks.sh approve all          # or: approve 003

Approving is your step: approve refuses to run inside a Claude Code session, and Claude is blocked from calling it or editing a task's status:.

3

Build it

/laravel:task

Sonnet takes the next runnable task and works through it: builds it (directly if small, with the full phased build if large), runs the checks, gets the verifier's verdict (section 6), closes it with a log line, and saves what it learned.

draft → you approve → todo → doing → done or review or blocked

6. How a task is checked

The builder can't mark its own work done. tasks.sh close refuses until a verdict is recorded: new in 2.3

VerdictWhat happens
PASSEvery criterion was proven. The task closes as done.
FAILThe builder fixes exactly what failed and the verifier checks again. After two failed rounds the task is blocked.
UNVERIFIEDEverything else passed, but a [browser] criterion couldn't be seen (no dev server or Playwright). The task goes to review, not done. Its log names what to check; when you've checked it, run tasks.sh accept <id> in your own terminal. Tasks that depend on it wait until then.
SKIPPEDOnly for tiny changes: every criterion is [review] and the diff is at most 20 lines.

7. Running many tasks safely

Running tasks one after another in a single conversation lets context pile up, and quality drops by the 4th or 5th task. So /laravel:task all stops after 3. For longer batches use the runner, which starts a fresh session for every task:

bash .claude/hooks/run-tasks.sh --checkpoint                # all runnable tasks, in order
bash .claude/hooks/run-tasks.sh 004 005 --budget 3          # just these, max $3 each
OptionEffect
--checkpointOne local git commit per finished task, on a new branch nw/batch-<time> so main is never touched. Each commit holds only that task's files: never .env or keys, never edits that were already there.
--no-branchWith --checkpoint, commit on the current branch instead
--budget USDSpending limit per task
--max NStop after N tasks
--dry-runShow what would run, and run nothing

The runner stops at the first task that doesn't finish (blocked, failed or over budget); run it again and it continues from there. A task that ends in review doesn't stop the batch: the runner tells you to check it and moves on to tasks that don't depend on it.

Undo one task (needs --checkpoint): bash .claude/hooks/tasks.sh undo 004. If later finished tasks depend on it, add --cascade to undo those first, newest first.

When the batch looks good, run /laravel:sync (section 8). Claude can't push or open pull requests on its own.

8. Git: one command to commit, pull, push

One command does the whole round. Only you can start it, so Claude never runs it on its own: new

/laravel:sync [commit message]
StepWhat happens
1. CommitStages everything not ignored, refuses secret files, and commits with a message in your project's style (or yours, if you pass one).
2. PullBrings this branch's own remote commits and then the stage branch into the current branch (merge by default). Clear conflicts are resolved; unclear ones stop everything and are explained.
3. CheckIf anything came in, the tests run again. A failure stops the push.
4. PushPushes the branch. It never pushes a branch that doesn't contain the stage branch's latest commit, and never force-pushes.
1

Tell it your stage branch once

./install.sh /path/to/app --stage-branch stage          # at install, or:
/laravel:setup                                             # asks, suggesting stage/staging/develop

It's stored in .claude/workflow.conf (STAGE_BRANCH=stage, SYNC_MODE=merge). Commit that file so the team shares it. If it's missing, the first /laravel:sync asks.

A plain git push from Claude is always blocked and redirected, so no push can skip the stage pull. The git work is done by git-sync.sh (status, sync, push, stage, candidates), which you can also run in your own terminal. With the Laravel kit, a push happens only after you type /laravel:sync (that counts as your go-ahead for that turn only); asking in plain words commits but doesn't push.

Every check hit is recorded in .claude/.cache/metrics.jsonl. tasks.sh stats summarises them.

12. Post and Page content: Gutenberg

Every Post, Page, News or Article module uses WordPress's own block editor (@wordpress/block-editor), mounted as a small React component in your Blade form through Vite. It never uses CKEditor or TinyMCE.

  • Storage: content holds the block format (exactly like WordPress); content_html is a sanitized copy made when you save.
  • Display: the public page outputs {!! $post->content_html !!}, the only unescaped output allowed.
  • Images: they upload through a protected Laravel route to your disk or CDN.
  • Tests: the planner adds them automatically: harmful HTML is stripped, authors can't edit each other's posts, and the editor saves a heading, a paragraph and an image.

Why not Laraberg? Its last release was in January 2023, and it relies on React 17, jQuery and Moment.

13. Redis, uploads, S3 and CDN

  • Redis: phpredis is preferred (predis if your project already uses it). Cache data lives on its own connection. Every cached value needs a way to be cleared. Use tags only on Redis or Memcached. Never use KEYS or Cache::flush() on a shared Redis. On Laravel 13, cache arrays, not models.
  • Uploads: validate with File::image()->max('5mb')->dimensions(…) (SVG is rejected by default). Store with random names, never the client's file name.
  • Public vs private: public files use storePublicly and are served from the CDN. Private files are stored privately and served with temporaryUrl() after a permission check.
  • CDN: set AWS_URL=https://cdn.example.com and Storage::url() returns CDN links. Store paths in the database, never full URLs. Never-changing file names with long cache headers mean you never have to purge the CDN.
  • Images: resize, convert to WebP and create size variants in a queued job, not during the request.

15. A typical day

  1. /laravel:write-task …, then answer its questions.
  2. Read the drafts in .claude/tasks/, then tasks.sh approve all in your own terminal.
  3. Optional: start php artisan serve and set LARAVEL_WF_DEV_URL so browser checks really run.
  4. bash .claude/hooks/run-tasks.sh --checkpoint and let it work, or /laravel:task for one at a time.
  5. Check the result. For tasks in review, check the criteria named in their log, then tasks.sh accept <id>. Undo any task you don't like with tasks.sh undo <id>.
  6. /laravel:review, then /laravel:ship. When everything is green, /laravel:sync: it pulls the stage branch in, re-runs the tests and pushes.
  7. Now and then, run tasks.sh stats to see cost, time, the verifier's pass rate and which checks fire most.

"task is still a draft"Read it, then tasks.sh approve <id> in your own terminal.

17. What's new in 2.4 and 2.3

ChangeWhat it means for you
Git commands 2.4/laravel:sync commits, pulls the stage branch in, checks and pushes in one go. Every push pulls the stage branch in first (section 8).
Plugin install 2.4Install once, update with one command, nothing copied into projects (section 3). The commands stay /laravel:*; the session report prints where the helpers are.
Plugin safety 2.4Guards always run, even if a project file tries to replace one. The kit's helpers are approved only by the plugin's own absolute path, and verify commands only with plain file arguments.

18. Measuring the workflow

./test.sh                          # the kit's self-test, against throwaway fixtures
bash evals/run.sh --reference      # free: proves every eval check can pass on a real Laravel app (must be 5/5)
bash evals/run.sh                  # 3 real agent runs (costs API money)

Results land in evals/results/. Compare them before and after changing any command, agent or skill. A change that lowers the pass rate or raises the cost is a regression.
